# 05 API Contract

`apps/api/src/modules/docs/openapi.ts` is the complete machine-readable route contract and backs `GET /openapi.json` and `GET /docs`. Keep this page compact: it is an endpoint inventory plus cross-cutting conventions. Put app examples, webhook verification code, idempotency examples, permission matrices, Channel Point adopt/release guidance, and redemption workflow details in [`README.integration.md`](README.integration.md).

## Conventions

- App-facing APIs are versioned under `/api/v1` and use `Authorization: Bearer <app_api_key>`. App API keys are generated by admins, the raw key is shown once, and only a prefix/hash is stored. See the [integration guide](README.integration.md#2-generate-an-api-key).
- Admin APIs are under `/api/admin` and require `INTERNAL_ADMIN_API_KEY` via `X-Admin-API-Key: <key>` or `Authorization: Bearer <key>`, except Twitch OAuth browser callbacks. Keep admin surfaces private/proxy-protected. See the [security guide](11_SECURITY.md) and [integration guide](README.integration.md#1-register-an-app).
- Downstream app webhooks are HMAC-signed and must be verified against the raw request body before parsing JSON. See [webhook verification](README.integration.md#5-receive-and-verify-webhooks).
- Twitch EventSub ingestion and downstream webhook handling are idempotent/deduped. Apps should store idempotency records before side effects. See [idempotency expectations](README.integration.md#idempotency-expectations).
- Outgoing chat sends require stable `idempotency_key` values; same-key/different-body conflicts are rejected instead of sending duplicate chat messages. See [client examples](README.integration.md#62-send-chat-with-a-stable-idempotency_key).
- Health checks: `/health/live` is process liveness, `/health/ready` gates readiness, and `/health/deep` reports degraded dependencies such as Twitch setup/scopes, EventSub, queues, Channel Points, and dead letters. Inspect failures in Admin diagnostics, Twitch/EventSub status, queue views, webhook deliveries, and dead-letter views. See [consumer health checks](README.integration.md#health-checks-for-consumers) and the [deployment guide](README.deployment.md).

## Public docs and callbacks

```text
GET  /openapi.json
GET  /docs
POST /webhooks/twitch/eventsub
GET  /api/v1/twitch/oauth/bot/callback
GET  /api/v1/twitch/oauth/broadcaster/callback
```

`POST /webhooks/twitch/eventsub` verifies Twitch raw-body HMAC signatures, handles challenge/notification/revocation messages, and dedupes Twitch message IDs.


### Chat

### Channel status and public channel data

### Channel Points

```text
GET    /api/v1/channel-points/rewards?include_deleted=
POST   /api/v1/channel-points/rewards
POST   /api/v1/channel-points/rewards/sync
GET    /api/v1/channel-points/rewards/:rewardId
PATCH  /api/v1/channel-points/rewards/:rewardId
DELETE /api/v1/channel-points/rewards/:rewardId
POST   /api/v1/channel-points/rewards/:rewardId/adopt
POST   /api/v1/channel-points/rewards/:rewardId/release
GET    /api/v1/channel-points/rewards/:rewardId/redemptions?status=&sync=&limit=
GET    /api/v1/channel-points/redemptions?status=&limit=
PATCH  /api/v1/channel-points/rewards/:rewardId/redemptions/:redemptionId/status
```

Adopt/release is for binding or unbinding existing Twitch rewards without creating/deleting the Twitch reward. Hatchery should adopt only rewards it will manage through the gateway; shared, broadcaster-run, unmanaged, or observed-only rewards should remain admin-managed. Full examples and rules live in the [integration guide](README.integration.md#65-adopt-or-release-existing-channel-point-rewards).

Redemption status updates accept `FULFILLED` or `CANCELED`. The gateway never auto-fulfills or auto-cancels; Hatchery decides after its economy logic and calls the status endpoint explicitly. See [redemption status examples](README.integration.md#66-fulfill-or-cancel-channel-point-redemptions).

### Subscriptions and Bits

```text
GET  /api/v1/subscriptions
GET  /api/v1/bits/leaderboard
```

### Events, logs, and app-owned delivery diagnostics

```text
GET  /api/v1/events?type=&limit=
GET  /api/v1/events/:eventId
GET  /api/v1/webhook-deliveries?status=&limit=
GET  /api/v1/webhook-deliveries/:deliveryId
POST /api/v1/webhook-deliveries/:deliveryId/retry
```

Access to logs is permission-based. Apps see their own deliveries and permitted channel events; full raw logs remain admin-only by default.

For TrueNAS/reverse proxy deployments, publish the Twitch EventSub webhook and OAuth callback paths through HTTPS, but keep `/api/admin/*` and the admin UI private or protected at the proxy before requests reach the gateway.

Queue inspection and retry admin endpoints intentionally use the implemented resource-specific route names above: `/api/admin/outgoing-chat/messages*` for outgoing chat messages and `/api/admin/webhook-deliveries*` for webhook deliveries. Do not document `/api/admin/queues/*` as an active route unless queue aliases are intentionally added later.
